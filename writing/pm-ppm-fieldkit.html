I turned 49 PM tasks into a Claude plugin

July 2026 · 6 min read

Most of the work a PM or PPM does has a shape you already know before you start. A market requirements doc has a shape. A competitive battle card has a shape. A win-loss writeup has a shape. And yet almost every time, we start from a blank page and rebuild that shape from memory, at whatever quality our energy that day allows.

I run continuous discovery and map opportunity trees as part of how I work, and somewhere in that process I started wondering whether the shape itself, not just the content, could be handed to Claude. Not "write me a battle card," which just moves the blank page problem onto the model. Something closer to a real process: ask the right questions first, then produce a complete, structured output, every time, the same way a good analyst would.

Mapping the whole lifecycle

I'm Pragmatic Marketing Level 4 certified, and that framework already has a well-defined taxonomy for everything a PM/PPM org does, from early market discovery through launch and post-launch metrics. Instead of picking one task to automate, I mapped the whole thing: 49 distinct activities, grouped roughly into discovery, strategy, planning, go-to-market, enablement, and ongoing operations.

Each one became a Claude Code skill with the same three-part shape:

  1. Intake — a short set of questions to ground the output in real context: product, segment, source material, target format. No generation starts until this is answered.
  2. Structured output — a defined document shape, not a freeform essay. A market requirements skill always produces the same sections: problem landscape, prioritized requirements, success criteria, out of scope.
  3. Save offer — every skill ends by offering to save the output as a file, so the work leaves the chat window instead of dying there.
What surprised me: the intake step mattered more than the output template. The first version of this skipped straight to generation, and the outputs were fine, generic-fine. Forcing five questions before anything gets written is what actually made the difference between a template and something you'd send to a stakeholder.

What it's actually for

Ask for a competitive battle card, and the skill asks which competitor, which deal context, and what format, before producing a structured card with positioning, objection handling, and proof points. Ask for a win-loss analysis, and it walks through the same discipline: intake, structure, save. Forty-nine times over, covering the full lifecycle a PM/PPM org actually runs.

This started as something I built to solve a problem I kept hitting in my own work. What's published here is a from-scratch, fully generic rebuild, no proprietary integrations, no company-specific data, built to work with whatever tools and document systems you already use.

What's next

The obvious gap right now is that each skill runs independently. A positioning doc built today and a battle card built next month don't know about each other. The natural next step is a shared context layer so outputs built from the same underlying product stay consistent with each other automatically, without a human being the one who has to remember to cross-check.

If you try this and hit a rough edge, I'd genuinely like to hear about it.
