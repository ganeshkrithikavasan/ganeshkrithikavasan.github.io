Email Commitment Finder

A small AI system that finds commitments and deadlines in email. It also says when it is not sure.

This system reads email and figures out two things.

  1. Does this email contain a commitment or a deadline? If so, what is it? Who made it? How sure are we?
  2. Who and what is this email about? Emails mention the same client, deal, or project in many different ways. This project links those mentions into one clear picture.

I am using a well known public dataset, Enron. It is not someone's private inbox.

Personal goal for building this project

I've spent 15 years in R&D and product management. For the last several years, I have focused on AI products in legal tech.

Before writing any code, here is a question I would ask if someone else had built it. When does it save a person time? When does it become one more thing they have to double check?

If I were scoping this as a product, I would ask a few more questions.

  • How often is the system confident? How often does it have to say "I'm not sure"? A system that is usable only a fifth of the time saves nobody work.
  • Which mistake costs more? Missing a real deadline, or flagging something that is not one. I will not tune for the wrong one.
  • What does it cost per email to run on different models? Does that number still make sense at production scale? I am answering this with a real side by side comparison. The same extraction task runs on a frontier model, Claude Sonnet. It also runs on a local model, DeepSeek-R1 14B through Ollama on my own machine. Let's put those GPUs to work! My goal is not to prove the free model is just as good. I want to see what it costs in quality to bring the cost down, and where that tradeoff stops being worth it.
  • Does "I'm not sure" make people ignore the system? Do they stop using it entirely after it catches one wrong answer?
  • Can the system explain its decisions? In a legal or compliance adjacent workflow, this is not optional.

Those are the questions I would ask as an AI PM. I am answering them myself, with the system I am designing and building.

How I'm building it

Every email goes through a small pipeline.

  1. Extract. An AI model reads the email. It pulls out any commitments or deadlines it finds. Then it gives each one a confidence score.
  2. Check. A second, independent pass reviews the extraction. Part of this check is another AI model. Part of it is traditional Python code. The code asks two simple things. Does the date actually exist? Is the confidence score in a valid range? Mixing an AI check with a hard-coded check catches different kinds of mistakes.
  3. Decide. If the extraction is solid and both checks agree, the system accepts it. If not, it tries again once, now knowing the difference or disagreement. If it is still unclear, it marks the result "unsure" and flags it for a person to review. Instead of guessing and hoping, the system hands the decision to a human. This is the "human in the loop" part.
  4. Record and audit. Every decision is logged. The log holds the input, the output, and how confident the system was. It also holds the exact prompt and model versions, and what the run cost in time and tokens.

That loop of extract, check, decide, record is our project's harness.

Stages

  1. Get the core loop working on real email. Extract, check, decide, record.
  2. Add memory for people and companies. Use embeddings, which turn text into numbers that capture meaning. The system then recognizes that "Acme Corp," "Acme," and "the Acme deal" are the same thing, even across different emails.
  3. Turn it into tools an AI agent can call via MCP.
  4. Run evals and cost analysis. Build a real evaluation set. Check accuracy, how often it makes things up, how fast it is, and what it costs to run. This is also where the Sonnet vs. DeepSeek-R1 tokenomics comparison lives. Same pipeline, same prompts, one frontier model and one local model, run side by side. The cost and quality tradeoff gets measured, not guessed.
  5. Write it up. What was built. What worked. What didn't. What I would do differently at scale. The goal is a production-ready product.
